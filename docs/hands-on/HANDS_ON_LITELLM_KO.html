Claude Code와 브리지 사이에
LiteLLM 게이트웨이 두기

가상 키와 요청 로그가 필요할 때 쓰는 구성입니다. 터미널 A에서 브리지와 LiteLLM을 띄우고, 터미널 B의 Claude Code가 LiteLLM을 거쳐 Copilot 모델로 답하게 만듭니다.

  • 약 20분 (LiteLLM 첫 설치 포함)
  • 터미널 2개 (A · B)
  • 필요: uv, Copilot 로그인
  • 프롬프트는 운영자의 Copilot 좌석을 사용
먼저 알아둘 것 → 영상으로 먼저 보기

LiteLLM은 anthropic/* 공급자로 브리지에 연결합니다. Copilot 모델만 쓰면 된다면 실습 가이드 ① Direct가 더 간단합니다.

영상으로 먼저 보기

두 개의 터미널(A·B)을 오가며 진행하는 전체 과정을 실제 녹화로 보여 줍니다. 장면 버튼을 누르면 그 부분부터 재생합니다.

영상 파일(HANDS_ON_LITELLM_KO.mp4)을 이 HTML과 같은 폴더에 두면 재생됩니다.

먼저 알아둘 것

LiteLLM을 끼우면 얻는 것과 잃는 것이 있습니다. 시작 전에 한 번만 확인하세요.

터미널 A게이트웨이 운영자

브리지와 LiteLLM 서버를 띄우고 계속 열어 둡니다. 저장소, npm ci, copilot login, uv가 필요합니다.

터미널 B클라이언트

Claude Code를 실행합니다. 게이트웨이 주소와 키만 있으면 되고, npm ci와 copilot login은 필요 없습니다.

구분내용
얻는 것LiteLLM의 가상 키(키마다 접근 제어)와 요청 로그를 Claude Code 앞단에 둘 수 있습니다.
잃는 것Claude Code의 1M 컨텍스트 창(별칭은 기본 200K), /model의 브리지 모델 목록, 브리지 자체의 토큰 계산.
맞지 않는 것LiteLLM의 비용 추적과 예산은 Copilot 모델에서 맞지 않습니다. 사용량은 GitHub Copilot AI Credits로 확인하세요.
좌석 공유 주의

브리지 하나는 GitHub Copilot 좌석 하나입니다. 게이트웨이를 거친 모든 요청은 어느 키로 보냈든 운영자의 좌석으로 과금되고 운영자 조직의 정책을 따릅니다. 그래서 팀이 함께 쓰는 게이트웨이는 권장하지 않습니다. 이 가이드는 같은 PC에서 혼자 써 보는 구성입니다.

이 구성은 처음부터 끝까지 검증되지 않았습니다

핵심 검증은 LiteLLM을 시작하지 않고 Claude Code를 브리지에 직접 연결해 실행합니다. 이 가이드의 화면은 아래 환경에서 한 번 실제로 따라 한 결과입니다.

1

터미널 A준비 확인

저장소, 로그인, uv가 준비됐는지 확인합니다.

약 2분
  1. 실습 가이드 ① 1~2단계(설치, copilot login)를 마쳤는지 확인하세요.
  2. uv가 있는지 확인하세요. LiteLLM 설치 스크립트가 Python 3.13 환경을 만들 때 씁니다. 없으면 설치하세요(macOS: brew install uv).
  3. 이후 모든 명령은 저장소 폴더에서 실행합니다. 터미널 A는 브리지·LiteLLM 서버용이고, 서버는 포그라운드에서 계속 실행되므로 실행 중인 터미널 A에 클라이언트 명령을 붙여 넣지 마세요.
터미널 A
cd ~/cc-mscp-sdk
uv --version
ls node_modules/@microsoft | head -n 2
성공 기준
  • uv --version이 버전을 출력합니다.
  • node_modules/@microsoft 안에 copilot-sdk가 보입니다(npm ci 완료).

2

터미널 A브리지 포트 고정

LiteLLM이 늘 같은 포트로 브리지를 찾도록 GHCP_BRIDGE_PORT=4142를 고정합니다.

약 1분
  1. 셸 프로필에 한 줄을 추가하세요(Zsh 기준).
  2. 프로필은 이미 열린 셸에는 적용되지 않습니다. 새 셸을 열거나 exec zsh로 다시 불러오세요.
터미널 A
echo 'export GHCP_BRIDGE_PORT=4142' >> ~/.zshrc
exec zsh
echo $GHCP_BRIDGE_PORT
왜 고정하나요?

이 컴퓨터의 claude와 claude-ghcp는 print 모드(-p)를 뺀 모든 실행이 공유 브리지 하나를 씁니다. 포트를 지정하지 않았거나 다른 포트를 요청한 실행은 게이트웨이의 브리지를 교체해 LiteLLM이 멈춥니다. 같은 export를 claude/claude-ghcp를 쓸 모든 터미널에 적용하세요.

성공 기준
  • echo $GHCP_BRIDGE_PORT가 4142를 출력합니다.

3

터미널 A브리지 시작하고 토큰 받기

브리지를 4142 포트에 띄우고, LiteLLM이 쓸 브리지 토큰을 환경 변수에 담습니다.

약 2분
  1. 아래 블록을 통째로 복사해 붙여 넣으세요. 성공하면 아무것도 출력하지 않습니다.
  2. 이어서 브리지가 살아 있는지, 토큰이 맞는지 확인하세요.
터미널 A — 저장소 폴더
if [ -z "$GHCP_BRIDGE_PORT" ]; then
  echo "GHCP_BRIDGE_PORT가 비어 있습니다. 2단계를 마친 뒤 새 셸을 여세요." >&2
else
  export GHCP_BRIDGE_URL="http://127.0.0.1:$GHCP_BRIDGE_PORT"
  unset GHCP_BRIDGE_TOKEN
  BRIDGE_JSON="$(node src/bridge-daemon.mjs ensure claude-sonnet-5 "$GHCP_BRIDGE_PORT")" &&
    export GHCP_BRIDGE_TOKEN="$(printf '%s' "$BRIDGE_JSON" |
      node -e 'let d="";process.stdin.on("data",c=>d+=c).on("end",()=>console.log(JSON.parse(d).token))')"
fi
터미널 A — 확인
curl --silent --show-error --fail "$GHCP_BRIDGE_URL/health" | grep -o '"ok":true'

printf 'x-api-key: %s\n' "$GHCP_BRIDGE_TOKEN" |
  curl --silent --show-error --fail -H @- "$GHCP_BRIDGE_URL/v1/models?all=true" |
  grep -o '"id":"claude-sonnet-5"'
성공 기준
  • "ok":true가 출력됩니다.
  • "id":"claude-sonnet-5"가 출력됩니다(브리지의 모델 목록에 이 모델이 있다는 뜻입니다).
토큰은 비밀번호처럼

토큰이 있으면 누구나 내 Copilot 좌석을 쓸 수 있습니다. 어느 로컬 사용자든 프로세스 인수를 읽을 수 있어서, 이 가이드의 curl은 키를 인수가 아니라 표준 입력(-H @-)으로 읽습니다. 화면에 출력하거나 공유하지 마세요.

실패하거나 아무것도 안 돼요
  • ensure가 이유를 출력하면 그 메시지를 먼저 읽으세요. SDK protocol version mismatch라면 unset COPILOT_CLI_PATH 후 다시 하세요.
  • GitHub Copilot model is unavailable: … — ./bin/ghcp-models에서 쓸 수 있는 모델을 고르세요(ensure의 모델 인수).
  • GHCP_BRIDGE_PORT가 비어 있습니다 — 2단계를 마친 뒤 새 셸에서 다시 실행하세요.
다음: LiteLLM 설치·시작 →
4

터미널 ALiteLLM 설치하고 시작하기

LiteLLM을 처음 한 번 설치하고 서버를 시작합니다.

설치 약 6분 + 시작
  1. 3단계와 같은 셸에서 로컬 런타임을 설치하세요. LiteLLM v1.97.0을 .runtime/에 내려받고 마스터 키도 만듭니다. 처음 한 번만 하면 되고, 촬영 환경에서는 약 6분 걸렸습니다.
  2. 설치가 끝나면 서버를 시작하세요. LiteLLM의 기본 포트는 4000이지만 다른 프로그램과 겹치기 쉬워서, 이 가이드는 LITELLM_PORT=4001로 시작합니다. 이 터미널은 열어 두세요.
터미널 A — 처음 한 번
npm run litellm:setup
터미널 A
LITELLM_PORT=4001 npm run litellm:start
성공 기준
  • 설치 마지막 줄이 LiteLLM v1.97.0 is ready.입니다.
  • 서버 로그에 Application startup complete가 보이고, 터미널 A가 계속 실행 중입니다.
알아두면 좋아요
  • litellm:start는 시작할 때 한 번만 터미널 A 셸의 GHCP_BRIDGE_URL·GHCP_BRIDGE_TOKEN을 읽습니다. 브리지가 교체되면 Ctrl-C로 멈추고 새 토큰을 받은 뒤 다시 시작하세요.
  • 기본 설정 파일(examples/litellm-github-copilot.yaml)은 고칠 필요가 없습니다. 모델 별칭 여섯 개가 모두 브리지를 가리킵니다.
시작하지 않아요
  • GHCP_BRIDGE_URL is required… / GHCP_BRIDGE_TOKEN is required… — 3단계를 실행한 같은 셸(터미널 A)에서 다시 실행하세요.
  • 포트 4001도 이미 사용 중 — 다른 번호로 시작하세요. 터미널 B의 LITELLM_BASE_URL도 같은 포트로 바꿔야 합니다.
    터미널 A
    LITELLM_PORT=4002 npm run litellm:start
  • 설치 중 오류 — 메시지를 해결한 뒤 npm run litellm:setup을 다시 실행하세요(이미 받은 것은 재사용합니다).

5

터미널 B클라이언트에서 연결 확인

새 터미널을 열고, 게이트웨이에 접근되는지 확인합니다.

약 1분
  1. 새 터미널(B)을 열고 터미널 A와 같은 저장소 폴더로 이동하세요. 터미널 A는 실행 중인 채로 두세요.
  2. 게이트웨이 주소, 키(저장소의 마스터 키 파일), 모델 별칭을 설정하고 모델 목록을 조회하세요.
터미널 B — 저장소 폴더
cd ~/cc-mscp-sdk
export LITELLM_BASE_URL="http://127.0.0.1:4001"
export LITELLM_API_KEY="$(tr -d '\n' < .runtime/litellm-master-key)"
export LITELLM_MODEL="claude-sonnet-5"

printf 'Authorization: Bearer %s\n' "$LITELLM_API_KEY" |
  curl --silent --show-error --fail -H @- "$LITELLM_BASE_URL/v1/models" |
  grep -o '"id":"[^"]*"'
성공 기준
  • 목록에 claude-sonnet-5가 있습니다.
두 가지 규칙
  • LITELLM_BASE_URL에는 /v1을 붙이지 않습니다. Claude Code가 /v1/messages를 덧붙이며, claude-litellm은 /v1로 끝나는 URL을 거부합니다.
  • 별칭에는 [1m]이나 [NNNk] 접미사를 붙이지 않습니다. LiteLLM이 400 Invalid model name으로 거부합니다.
연결이 안 돼요
  • 연결 실패(curl: (7)) — 터미널 A에서 LiteLLM이 실행 중인지, 포트가 같은지 확인하세요.
  • 401 — 키가 틀렸습니다. 키 파일이 없다면 터미널 B의 폴더와 4단계 설치 성공 여부를 확인하세요.

6

터미널 BClaude Code 실행

claude-litellm으로 LiteLLM을 거쳐 Copilot 모델과 대화합니다.

약 2분
  1. 5단계의 변수가 설정된 같은 터미널 B에서 런처를 실행하세요.
  2. 처음 여는 폴더라면 신뢰 확인 창이 뜹니다. 기본 선택이 No, exit이므로 ↓로 Yes, I trust this folder를 고른 뒤 Enter를 누르세요.
  3. OK라고 답해줘를 입력하고 Enter를 누르세요.
  4. 터미널 A로 돌아가 LiteLLM 로그에 요청이 찍혔는지 확인하세요.
  5. (선택) /model로 목록을 열어 보세요. 끝낼 때는 Esc로 목록을 닫고 /exit를 입력하세요. 클라이언트를 종료해도 운영자의 게이트웨이는 멈추지 않습니다.
터미널 B
./bin/claude-litellm
성공 기준
  • 터미널 B에서 질문하면 OK라는 답이 돌아옵니다.
  • 터미널 A의 LiteLLM 로그에 요청 처리 기록이 나타납니다.
Direct와 달라지는 점
  • /model 목록에는 LiteLLM · <별칭> 행이 나옵니다. 브리지의 Copilot 모델 목록은 나오지 않습니다.
  • Claude Code는 모든 별칭에 기본 컨텍스트 창(200K)을 씁니다. 1M 창이 필요하면 Direct 경로를 쓰세요.
  • 게이트웨이가 모델을 여러 개 제공하면 계열별로 지정할 수 있습니다: LITELLM_OPUS_MODEL, LITELLM_SONNET_MODEL, LITELLM_HAIKU_MODEL.
키가 파일에 저장됩니다

claude-litellm은 게이트웨이 주소와 키가 담긴 설정 파일(권한 0600)을 ${XDG_STATE_HOME:-~/.local/state}/claude-code-ghcp-sdk/litellm-settings/에 남깁니다(print 모드 제외). 키를 더 두고 싶지 않으면 그 디렉터리를 직접 지우세요.

요청이 실패해요
  • 400 Invalid model name — 별칭 오타이거나 [1m] 접미사입니다. 5단계의 목록에 나온 id를 쓰세요.
  • 401 authentication_error: Invalid bridge credential. — LiteLLM이 이전 토큰을 쓰고 있습니다(브리지가 교체됨). 아래 문제 해결 표를 보세요.
  • Invalid LiteLLM base URL: URL must not end in /v1 — LITELLM_BASE_URL에서 /v1을 빼세요.

중지하고 정리하기

쓰고 나면 LiteLLM과 브리지를 멈춥니다.

약 1분
  1. 터미널 A에서 Ctrl+C로 LiteLLM을 멈추세요.
  2. 브리지도 멈추려면 먼저 필요한 bridge.log 내용을 보관한 뒤 claude-ghcp-stop을 실행하세요.
터미널 A
./bin/claude-ghcp-stop
./bin/claude-ghcp-status
무엇이 남나요
  • claude-ghcp-stop은 이 브리지를 쓰던 이 컴퓨터의 모든 claude·claude-ghcp 세션(print 모드 제외)의 연결을 끊습니다.
  • 서비스를 멈춰도 2단계의 프로필 설정과 .runtime/(마스터 키 포함)은 지워지지 않습니다. 다시 운영할 계획이면 그대로 두세요.
  • 재부팅 후에는 브리지와 LiteLLM이 스스로 시작하지 않습니다. 터미널 A에서 3단계와 npm run litellm:start를 다시 실행하세요. 설치는 다시 할 필요가 없습니다.
다음: 이미 있는 게이트웨이에 연결 →

이미 운영 중인 게이트웨이에 연결만 하려면

다른 사람이 운영하는 게이트웨이의 URL과 키를 받았다면 터미널 B 쪽만 하면 됩니다. 브리지는 운영자의 컴퓨터에서 실행되므로 npm ci와 copilot login은 필요 없습니다.

터미널 B
git clone https://github.com/junwoojeong100/cc-mscp-sdk.git
cd cc-mscp-sdk

export LITELLM_BASE_URL="https://litellm.example.com"
export LITELLM_API_KEY="<받은 가상 키>"

printf 'Authorization: Bearer %s\n' "$LITELLM_API_KEY" |
  curl --silent --show-error --fail -H @- "$LITELLM_BASE_URL/v1/models"

export LITELLM_MODEL="claude-sonnet-5"
./bin/claude-litellm
  • curl이 성공하고 모델 목록을 돌려줄 때만 계속하세요. 목록의 id가 LITELLM_MODEL에 쓸 수 있는 별칭입니다.
  • LITELLM_BASE_URL에는 게이트웨이 루트 URL(/v1 없음)을 넣으세요.

문제 해결 한눈에 보기

브리지가 교체되면 토큰을 어디서 다시 읽나요?

토큰은 브리지 데몬 디렉터리의 bridge.json에 있습니다. macOS에서는 터미널 A에서 Ctrl-C로 LiteLLM을 멈춘 뒤 아래 명령으로 읽고 npm run litellm:start를 실행하세요. 3단계를 다시 실행하지 마세요 — 셸 환경이 다르면 브리지를 또 교체합니다.

터미널 A (macOS)
export GHCP_BRIDGE_TOKEN="$(node -pe \
  'JSON.parse(require("fs").readFileSync(process.argv[1], "utf8")).token' \
  ~/Library/Caches/claude-code-ghcp-sdk/bridge.json)"

Linux는 ${XDG_CACHE_HOME:-~/.cache}/claude-code-ghcp-sdk/bridge.json입니다.

이 가이드에 대해

  • 이 페이지의 화면과 영상은 아래 환경에서 실제로 실행해 캡처한 것입니다. 화면의 폴더는 촬영용이고, 브리지 토큰과 LiteLLM 마스터 키는 화면에 나오지 않도록 처리했으며, 패키지 저장소 주소는 가렸습니다.
  • Claude Code에서 GitHub Copilot 모델을 쓰는 비공식 통합입니다. LiteLLM 자체의 동작(만드는 URL, 전달하는 헤더, 거부하는 이름, 비용 계산 방식)은 npm run litellm:setup이 설치하는 v1.97.0 기준이며 이 저장소가 검증하지 않습니다.
  • LiteLLM이 브리지의 429/529를 그대로 넘기는지, 먼저 재시도하는지도 검증하지 않았습니다.
