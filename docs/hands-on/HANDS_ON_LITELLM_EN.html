Hands-on guide ② · Through LiteLLM

Put a LiteLLM gateway
between Claude Code and the bridge

Use this setup when you want a LiteLLM gateway in front of the bridge, for example to get request logs. Start the bridge and LiteLLM in Terminal A, then let Claude Code in Terminal B answer with a Copilot model through LiteLLM.

  • About 20 min (including the first LiteLLM install)
  • 2 terminals (A · B)
  • Needs: Copilot login, uv (only to install a new LiteLLM)
  • Prompts use the operator's Copilot seat

LiteLLM reaches the bridge through its anthropic/* provider. If you only need Copilot models, Hands-on guide ① Direct is simpler. If you already have a LiteLLM, pick the path that fits you under Know this first.

Know this first

Adding LiteLLM gets you some things and costs you others. Check them once before you start.

Pick the path that fits your situation
  • You don't have a LiteLLM yet. Follow steps 1–7 below in order. This is the guide's main flow, and it ends at step 7.
  • You already run your own LiteLLM. Don't install a new one; follow Add the bridge to an existing LiteLLM. You don't need uv, and that section is the whole path.
  • Someone else runs the gateway and gave you its URL and a key. Follow Connect to an existing gateway. You only do the Terminal B side, and that section is the whole path.

Terminal AGateway operator

Starts the bridge and the LiteLLM server and keeps them open. Needs the repository, npm ci and copilot login, plus uv if you install a new LiteLLM.

Terminal BClient

Runs Claude Code. All it needs is the gateway address and a key. npm ci and copilot login aren't required.

CategoryDetails
What you gainLiteLLM's request logs can sit between Claude Code and the bridge. Virtual keys (access control per key) would also need a PostgreSQL database, which this setup does not include.
What you loseClaude Code's 1M context window (aliases get the default 200K), /model showing the bridge's model list, and the bridge's own token counting.
What won't be accurateLiteLLM's cost tracking and budgets are wrong for Copilot models. Check your usage in GitHub Copilot AI Credits instead.
Caution: seat sharing

One bridge is one GitHub Copilot seat. Every request that goes through the gateway, whichever key sends it, is billed to the operator's seat and follows the operator's organization policy. That's why a gateway shared by a team is not recommended. This guide covers a solo setup that you try out on one PC.

This setup hasn't been verified end to end

The core verification runs Claude Code directly against the bridge, without starting LiteLLM. The screens in this guide come from one real run-through in the environment listed below.

1

Terminal ACheck prerequisites

Check that the repository, your login and uv are ready.

About 2 min
  1. Make sure you've finished Hands-on guide ①, steps 1–2 (install, copilot login).
  2. Check that uv is installed. The LiteLLM setup script uses it to create a Python 3.13 environment. If you don't have it, install it (macOS: brew install uv). If you are only adding the bridge to a LiteLLM you already run, skip this item.
  3. From here on, run every command in the repository folder. Terminal A is for the bridge and the LiteLLM server, and the server keeps running in the foreground, so don't paste client commands into a Terminal A that is running a server.
Terminal A
cd ~/cc-mscp-sdk
uv --version
ls node_modules/@microsoft | head -n 2
What success looks like
  • uv --version prints a version.
  • node_modules/@microsoft contains copilot-sdk (npm ci is done).

2

Terminal APin the bridge port

Pin GHCP_BRIDGE_PORT=4142 so LiteLLM always finds the bridge on the same port.

About 1 min
  1. Add one line to your shell profile (shown for Zsh).
  2. A profile change doesn't apply to shells that are already open. Open a new shell, or reload with exec zsh.
Terminal A
echo 'export GHCP_BRIDGE_PORT=4142' >> ~/.zshrc
exec zsh
echo $GHCP_BRIDGE_PORT
Why pin it?

On this computer, every claude and claude-ghcp launch except print mode (-p) uses one shared bridge. A launch that doesn't specify a port, or asks for a different one, replaces the gateway's bridge and LiteLLM stops working. Apply the same export in every terminal where you'll use claude or claude-ghcp.

What success looks like
  • echo $GHCP_BRIDGE_PORT prints 4142.
Next: Start the bridge →
3

Terminal AStart the bridge and get its token

Start the bridge on port 4142 and store the bridge token that LiteLLM will use in an environment variable.

About 2 min
  1. Copy the entire block below and paste it in. On success it prints nothing.
  2. Then check that the bridge is alive and the token works.
Terminal A — repository folder
if [ -z "$GHCP_BRIDGE_PORT" ]; then
  echo "GHCP_BRIDGE_PORT is empty. Finish step 2, then open a new shell." >&2
else
  export GHCP_BRIDGE_URL="http://127.0.0.1:$GHCP_BRIDGE_PORT"
  unset GHCP_BRIDGE_TOKEN
  BRIDGE_JSON="$(node src/bridge-daemon.mjs ensure claude-sonnet-5 "$GHCP_BRIDGE_PORT")" &&
    export GHCP_BRIDGE_TOKEN="$(printf '%s' "$BRIDGE_JSON" |
      node -e 'let d="";process.stdin.on("data",c=>d+=c).on("end",()=>console.log(JSON.parse(d).token))')"
fi
Terminal A — check
curl --silent --show-error --fail "$GHCP_BRIDGE_URL/health" | grep -o '"ok":true'

printf 'x-api-key: %s\n' "$GHCP_BRIDGE_TOKEN" |
  curl --silent --show-error --fail -H @- "$GHCP_BRIDGE_URL/v1/models?all=true" |
  grep -o '"id":"claude-sonnet-5"'
What success looks like
  • "ok":true is printed.
  • "id":"claude-sonnet-5" is printed (the bridge's model list includes this model).
Treat the token like a password

Anyone with the token can use your Copilot seat. Any local user can read a process's arguments, so the curl commands in this guide read the key from standard input (-H @-) instead of passing it as an argument. Don't print it on screen or share it.

It fails or nothing happens
  • If ensure prints a reason, read that message first. If it's SDK protocol version mismatch, run unset COPILOT_CLI_PATH and try again.
  • GitHub Copilot model is unavailable: … — pick a model you can use from ./bin/ghcp-models (it goes in the model argument of ensure).
  • GHCP_BRIDGE_PORT is empty — finish step 2, then run the block again in a new shell.
Next: Install and start LiteLLM →
4

Terminal AInstall and start LiteLLM

Install LiteLLM once, the first time, and start the server.

About 6 min to install + start
If you already run a LiteLLM

Skip this step and follow Add the bridge to an existing LiteLLM. Instead of installing a new LiteLLM, you add the bridge to the config of the one you already use. That section includes the connection check and running Claude Code, so it is all you need to follow (steps 5–7 are not needed).

  1. In the same shell as step 3, install the local runtime. It downloads LiteLLM v1.97.0 into .runtime/ and also creates a master key. You only need to do this once, and it took about 6 minutes in the recording environment.
  2. When the install finishes, start the server. LiteLLM's default port is 4000, but that's easy to collide with other programs, so this guide starts it with LITELLM_PORT=4001. Keep this terminal open.
Terminal A — first time only
npm run litellm:setup
Terminal A
LITELLM_PORT=4001 npm run litellm:start
What success looks like
  • The last line of the install is LiteLLM v1.97.0 is ready.
  • The server log shows Application startup complete, and Terminal A is still running.
Good to know
  • litellm:start picks up, once at startup, the GHCP_BRIDGE_URL and GHCP_BRIDGE_TOKEN from the Terminal A shell. If the bridge is replaced, stop LiteLLM with Ctrl-C, get the new token, and start it again.
  • You don't need to edit the default config file (examples/litellm-github-copilot.yaml). All six model aliases point at the bridge.
It won't start
  • GHCP_BRIDGE_URL is required… / GHCP_BRIDGE_TOKEN is required… — run it again in the same shell (Terminal A) where you ran step 3.
  • Port 4001 is in use too — start with a different number. You also have to change LITELLM_BASE_URL in Terminal B to the same port.
    Terminal A
    LITELLM_PORT=4002 npm run litellm:start
  • Error during the install — fix what the message says, then run npm run litellm:setup again (anything already downloaded is reused).
Next: Check the client connection →
5

Terminal BCheck the connection from the client

Open a new terminal and check that you can reach the gateway.

About 1 min
  1. Open a new terminal (B) and go to the same repository folder as Terminal A. Leave Terminal A running.
  2. Set the gateway address, the key (the master key file in the repository) and the model alias, then list the models.
Terminal B — repository folder
cd ~/cc-mscp-sdk
export LITELLM_BASE_URL="http://127.0.0.1:4001"
export LITELLM_API_KEY="$(tr -d '\n' < .runtime/litellm-master-key)"
export LITELLM_MODEL="claude-sonnet-5"

printf 'Authorization: Bearer %s\n' "$LITELLM_API_KEY" |
  curl --silent --show-error --fail -H @- "$LITELLM_BASE_URL/v1/models" |
  grep -o '"id":"[^"]*"'
What success looks like
  • The list contains claude-sonnet-5.
Two rules
  • In LITELLM_BASE_URL, don't add /v1. Claude Code appends /v1/messages itself, and claude-litellm rejects a URL that ends in /v1.
  • Don't add a [1m] or [NNNk] suffix to the alias. LiteLLM rejects it with 400 Invalid model name.
Can't connect
  • Connection failed (curl: (7)) — check that LiteLLM is running in Terminal A and that the port is the same.
  • 401 — the key is wrong. If the key file is missing, check Terminal B's folder and whether the step 4 install succeeded.
Next: Run Claude Code →
6

Terminal BRun Claude Code

Chat with a Copilot model through LiteLLM using claude-litellm.

About 2 min
  1. In the same Terminal B where you set the step 5 variables, run the launcher.
  2. If it's the first time you open this folder, a trust prompt appears. The default choice is No, exit, so press ↓ to select Yes, I trust this folder, then press Enter.
  3. Type Reply with OK and press Enter.
  4. Go back to Terminal A and check that the request shows up in the LiteLLM log.
  5. (Optional) Open the list with /model. When you're done, press Esc to close the list and type /exit. Quitting the client does not stop the operator's gateway.
Terminal B
./bin/claude-litellm
What success looks like
  • When you ask in Terminal B, the answer OK comes back.
  • Terminal A's LiteLLM log shows a record of the request being handled.
How this differs from Direct
  • The /model list shows LiteLLM · <alias> rows. It doesn't show the bridge's Copilot model list.
  • Claude Code uses the default context window (200K) for every alias. If you need the 1M window, use the Direct path.
  • If the gateway serves several models, you can set one per family: LITELLM_OPUS_MODEL, LITELLM_SONNET_MODEL, LITELLM_HAIKU_MODEL.
Your key is saved to a file

claude-litellm leaves a settings file (mode 0600) that contains the gateway address and your key in ${XDG_STATE_HOME:-~/.local/state}/claude-code-ghcp-sdk/litellm-settings/ (except in print mode). If you don't want to keep the key around, delete that directory yourself.

The request fails
  • 400 Invalid model name — the alias has a typo or a [1m] suffix. Use an id from the step 5 list.
  • 401 authentication_error: Invalid bridge credential. — LiteLLM is using an old token (the bridge was replaced). See the troubleshooting table below.
  • Invalid LiteLLM base URL: URL must not end in /v1 — in LITELLM_BASE_URL, drop the /v1.

Stop and clean up

When you're done, stop LiteLLM and the bridge.

About 1 min
  1. In Terminal A, press Ctrl+C to stop LiteLLM.
  2. To stop the bridge too, first save any bridge.log content you need, then run claude-ghcp-stop.
Terminal A
./bin/claude-ghcp-stop
./bin/claude-ghcp-status
What's left behind
  • claude-ghcp-stop disconnects every claude and claude-ghcp session on this computer that was using this bridge (print mode excluded).
  • Stopping the services doesn't remove the profile setting from step 2 or .runtime/ (master key included). If you plan to run the gateway again, leave them in place.
  • After a reboot, the bridge and LiteLLM don't start on their own. In Terminal A, run step 3 and npm run litellm:start again. You don't need to repeat the install.
Done! If you're stuck: Troubleshooting table →

If you only need to connect to a gateway that's already running

If someone else runs the gateway and gave you its URL and a key, you only need the Terminal B side. The bridge runs on the operator's computer, so you don't need npm ci or copilot login.

Terminal B
git clone https://github.com/junwoojeong100/cc-mscp-sdk-v2.git cc-mscp-sdk
cd cc-mscp-sdk

export LITELLM_BASE_URL="https://litellm.example.com"
export LITELLM_API_KEY="<the API key you received>"

printf 'Authorization: Bearer %s\n' "$LITELLM_API_KEY" |
  curl --silent --show-error --fail -H @- "$LITELLM_BASE_URL/v1/models"

export LITELLM_MODEL="claude-sonnet-5"
./bin/claude-litellm
  • Continue only if curl succeeds and returns a model list. The id values in the list are the aliases you can use for LITELLM_MODEL.
  • Set LITELLM_BASE_URL to the gateway's root URL (no /v1).
  • In Claude Code, type Reply with OK. A reply means one request through that gateway worked. Leaving with /exit doesn't stop the operator's gateway, and your prompts use the operator's Copilot allowance.

If you already run your own LiteLLM

Skip the install and start in step 4 and add the bridge to your LiteLLM's config as one more model. Your existing models, keys and settings stay as they are. Your LiteLLM has to run on the same computer as the bridge, which only accepts requests on 127.0.0.1. Work through the five items below in order and you are done; you do not need to go back to steps 5–7.

  1. Terminal APrepare the bridge. Follow steps 1 (skip the uv check), 2 (pin the bridge port) and 3 (start the bridge, get the token) above, and no further. If you have already done step 3, this item is done. That shell then holds GHCP_BRIDGE_URL and GHCP_BRIDGE_TOKEN.
  2. Terminal AAdd the models to your config. Add the entries below to your LiteLLM config file, under the top-level keys it already has. Give model_name a new name that your config does not use yet (see the cautions below). YAML keeps only the last copy of a repeated key, so a second model_list: or litellm_settings: block would replace the first.
    Add to your LiteLLM config file
    model_list:
  # ...your existing models...
  - model_name: copilot-claude-sonnet-5
    litellm_params:
      model: anthropic/claude-sonnet-5
      api_base: os.environ/GHCP_BRIDGE_URL
      api_key: os.environ/GHCP_BRIDGE_TOKEN

litellm_settings:
  # ...your existing settings...
  model_group_settings:
    forward_client_headers_to_llm_api:
      - copilot-claude-sonnet-5
    Add one model_list entry per Copilot model (an ID from ./bin/ghcp-models goes after anthropic/), and list each new model_name under forward_client_headers_to_llm_api too.
  3. Terminal ARestart LiteLLM. In the same shell, restart your LiteLLM the way you normally start it. LiteLLM reads os.environ/ values once, at startup.
    Terminal A
    litellm --config /absolute/path/to/your-config.yaml
  4. Terminal BCheck the connection. Open a new terminal, enter this repository's folder, and list the models with your LiteLLM's URL and key and the new alias. Continue when the new alias is printed. Leave /v1 off the URL.
    Terminal B — repository folder
    cd ~/cc-mscp-sdk
export LITELLM_BASE_URL="http://127.0.0.1:4000"  # your LiteLLM's root URL
export LITELLM_API_KEY="<your LiteLLM key>"
export LITELLM_MODEL="copilot-claude-sonnet-5"

printf 'Authorization: Bearer %s\n' "$LITELLM_API_KEY" |
  curl --silent --show-error --fail -H @- "$LITELLM_BASE_URL/v1/models" |
  grep -o '"id":"copilot-claude-sonnet-5"'
  5. Terminal BRun Claude Code. In the same terminal, start the launcher. If it's the first time you open this folder, a trust prompt appears. The default choice is No, exit, so press ↓ to select Yes, I trust this folder, then press Enter. Then type Reply with OK and press Enter. An OK reply means it works. Type /exit to leave.
    Terminal B
    ./bin/claude-litellm
Success criteria — you are done when both of these are true
  • Step 4 prints "id":"copilot-claude-sonnet-5". Your LiteLLM knows the new alias.
  • In step 5, Reply with OK gets an OK answer. The question went through Claude Code → your LiteLLM → the bridge → Copilot.
Extra care with an existing LiteLLM
  • Use a new alias name. Entries that share a model_name form one group, and LiteLLM spreads requests across them. Reusing a name you already serve, such as claude-sonnet-5, sends some of the other provider's requests to your Copilot seat.
  • Forward headers for this alias only. The model_group_settings above is enough. forward_client_headers_to_llm_api: true under general_settings passes every client's x- headers to every provider your gateway calls.
  • Seat sharing. Every request to this alias runs on your Copilot seat, whoever sends it. If others use your LiteLLM, limit each key's or team's models.
  • If the bridge is replaced, its token changes. Give LiteLLM the new token and restart it; that briefly cuts off every model your LiteLLM serves.
When you're done — what to do next
  • Keep using it. Run ./bin/claude-litellm again in Terminal B. In a new terminal, run step 4's cd and the three export lines first.
  • When you're finished. /exit closes only Claude Code. If you no longer need the bridge, first save any bridge.log lines you need, then run ./bin/claude-ghcp-stop (every session that uses this bridge loses its connection). Stop LiteLLM the way you normally do, and if you don't want the Copilot entries any more, delete them from your config and restart it. The settings file claude-litellm leaves behind contains your LiteLLM key; delete it as step 6 describes if you don't want it kept.
  • If you're stuck. See the troubleshooting table below.

The config fields, the timeout and forward_llm_provider_auth_headers cautions, and troubleshooting are in the LiteLLM guide: Add the Bridge to an Existing LiteLLM.

Where do I re-read the token after the bridge is replaced?

The token is in bridge.json, in the bridge daemon's directory. On macOS, stop LiteLLM with Ctrl-C in Terminal A, read the token with the command below, then run npm run litellm:start. Don't run step 3 again — if your shell environment is different, it replaces the bridge once more.

Terminal A (macOS)
export GHCP_BRIDGE_TOKEN="$(node -pe \
  'JSON.parse(require("fs").readFileSync(process.argv[1], "utf8")).token' \
  ~/Library/Caches/claude-code-ghcp-sdk/bridge.json)"

On Linux the path is ${XDG_CACHE_HOME:-~/.cache}/claude-code-ghcp-sdk/bridge.json.
